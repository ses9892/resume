02

Netty 녹취 엔진과 연동 API

녹취는 RTP로 받습니다. RTP는 음성을 잘게 나눈 패킷이라, 순번과 시간이 붙어 있습니다. 한 통화 안에서도 고객이 말한 소리와 상담원이 말한 소리는 섞여 오지 않습니다. 고객 마이크는 RX, 상담원 마이크는 TX로 각각 들어옵니다.

엔진은 이 두 스트림을 같은 통화 키로 찾아 채널 하나에 넣습니다. 채널 1개가 동시 녹취 1건이고, 라이선스도 그 채널을 1개로 셉니다. 음원이 둘이라고 라이선스가 2개가 되지는 않습니다. 저장할 때는 RX와 TX의 순번을 맞춰 한 통화 파일로 남깁니다.

03

PostgreSQL 함수 · 프로시저 약 20개를 JPA 서비스로 전환

운영 DB가 Tibero로 바뀌면서 PostgreSQL 함수 · 프로시저를 그대로 쓸 수 없었습니다. 워크플로우를 이루는 약 20개를 JPA 서비스 코드로 하나씩 옮겼습니다.

어려웠던 부분은 프로시저가 다른 프로시저 · 함수를 호출하는 구조였습니다. DB 안에서는 안쪽 호출이 모두 바깥 프로시저의 트랜잭션 안에서 실행되지만, 자바로 옮기면 트랜잭션 범위를 코드에서 직접 정해야 합니다.

전환 전 · DB 안에서 실행

트랜잭션 1개 · 경계 최상위 프로시저 여기서 시작하고 여기서 커밋
같은 트랜잭션 프로시저 A 바깥 트랜잭션 안에서 실행
같은 트랜잭션 함수 B 조회 · 계산
같은 트랜잭션 프로시저 C 바깥 트랜잭션 안에서 실행

하나라도 실패하면 전체가 롤백됩니다.

전환 후 · 경계는 진입점 한 곳

@Transactional · 경계 WorkflowService.run() 최상위 프로시저에 대응 · 여기서 시작하고 여기서 커밋
REQUIRED · 참여 AService 구 프로시저 A · 바깥 트랜잭션에 합류
트랜잭션 없음 BCalculator 구 함수 B · 조회 · 계산만
REQUIRED · 참여 CService 구 프로시저 C · 바깥 트랜잭션에 합류
REQUIRES_NEW · 필요한 곳만 실패와 무관하게 남아야 하는 처리 본 작업이 롤백돼도 따로 커밋
01 · 경계는 진입점 한 곳

최상위 프로시저에 대응하는 서비스 메서드 하나에만 @Transactional을 둡니다. 하위 단계는 기본 전파(REQUIRED)로 같은 트랜잭션에 참여합니다.

그래서 원래 프로시저처럼 워크플로우 전체가 한 번에 커밋되거나 한 번에 롤백됩니다.

02 · 프로시저 단위로 빈 분리

같은 클래스 안에서 자기 메서드를 부르면 Spring 프록시를 거치지 않아 트랜잭션 설정이 적용되지 않습니다.

그래서 프로시저 하나를 서비스 빈 하나로 나눴고, 조회 · 계산만 하던 함수는 트랜잭션 없는 컴포넌트로 뺐습니다.

03 · 예외와 롤백 규칙

프로시저의 RAISE EXCEPTION은 자바 예외로 옮겼습니다. Spring은 기본적으로 런타임 예외에서만 롤백하므로, 체크 예외는 rollbackFor로 롤백 대상을 명시합니다.

하위 단계 예외를 바깥에서 잡고 넘기면 트랜잭션이 롤백 전용으로 표시돼 커밋 시점에 실패하므로, 예외는 삼키지 않고 경계까지 올립니다.

04

개발망 Jenkins · Shell CI/CD

CI/CD는 개발망에 구축했습니다. 개발 서버 안에서 Jenkins로 빌드하고, 서버마다 둔 Shell로 반영합니다. 운영망은 자동화하지 않았습니다.

개발망 · Step 01 / 빌드 · 담당
Jenkins로 개발 서버 안에서 빌드
개발망 서버에 Jenkins를 두고, 같은 기준으로 빌드가 나오게 했습니다.
개발망 · Step 02 / 배포 · 담당
서버별 Shell 스크립트 실행
개발 서버마다 배포 Shell을 두고, Jenkins가 그 스크립트를 호출해 서버별로 반영했습니다.
개발망 · Step 03 / 반영
WAS · 녹취 엔진 반영
JPA가 올라간 WAS와 Netty 녹취 엔진이 개발 서버에 같은 산출물로 반영됩니다.
운영망 · 수동
농협 내부 PCMS 결재 후 수동 배포
운영망은 우리은행과 같이 농협 내부 PCMS로 결재라인만 탄 뒤, 승인된 건을 수동으로 배포했습니다. Jenkins 파이프라인은 타지 않습니다.
개발망에서 난 효과

개발 반영을 서버마다 손으로 복사하지 않아도 됩니다. 빌드 기준이 하나라 개발 서버 간 산출물이 달라지지 않고, 녹취 엔진과 WAS를 같은 흐름으로 올릴 수 있습니다.

운영망은 분리

운영 반영은 결재가 끝난 뒤에만 진행됩니다. 개발 자동 배포와 운영 수동 배포가 나뉘어, 개발 중 배포가 운영 서버로 바로 들어가지 않습니다.

01RX · TX가 다른 이벤트 루프에서 같은 통화 상태를 동시에 수정

문제 · 동기화되지 않은 공유 상태

고객 RX
상담원 TX
루프 1

① RX를 루프 1에서 수신
② 루프 1이 통화 상태 수정
③ TX를 루프 2에서 수신
④ 루프 2도 동시에 수정

RX와 TX는 별도 RTP 스트림이라 서로 다른 Netty 채널로 받고, 두 채널이 다른 이벤트 루프에 배정될 수 있습니다. 두 루프가 같은 통화 객체(시퀀스 · 버퍼)와 라이선스 카운터를 동기화 없이 고치면 음원 순서가 섞이거나 라이선스 수가 어긋납니다. 그렇다고 이벤트 루프에서 락을 잡으면, 그 루프가 맡은 다른 통화의 수신까지 멈춰 병목이 됩니다.

수정 · 통화 상태는 담당 루프 한 곳, 라이선스는 원자 연산

고객 RX
상담원 TX

루프 2
통화 상태
① RX를 담당 루프 1에서 수신
② TX를 루프 2에서 수신
③ 담당 루프 1로 작업 전달
④ 루프 1만 통화 상태 수정

통화가 시작될 때 담당 이벤트 루프를 정하고, 다른 루프에서 받은 패킷은 eventLoop().execute()로 담당 루프에 넘겨 통화 상태를 한 스레드만 고치게 했습니다. 라이선스 카운터는 서버의 모든 통화가 함께 쓰는 값이라 루프에 묶지 않고 원자 연산(AtomicInteger)으로 증감하고, 통화 종료 때 반환이 두 번 일어나지 않게 종료 여부도 한 번만 바뀌도록 했습니다.

결과

통화 상태를 동시에 고치는 구간이 없어져 음원이 섞이지 않습니다. 락을 쓰지 않아 이벤트 루프가 대기로 멈추지 않고, 라이선스 사용 수는 실제 동시 통화 수와 맞습니다.

최상위 프로시저에 대응하는 WorkflowService.run()에만 @Transactional을 두고, 프로시저 단위로 나눈 A · C 빈은 REQUIRED로 같은 트랜잭션에 참여시켰습니다. 하위 단계 예외는 삼키지 않고 경계까지 올려, C가 실패하면 A까지 함께 롤백됩니다. 전환한 약 20개는 같은 입력으로 전환 전 프로시저 결과와 대조한 뒤 반영했습니다.

결과

워크플로우 약 20개가 전환 전과 같은 단위로 커밋 · 롤백되어 반쪽 데이터가 남지 않습니다. 트랜잭션 범위가 코드(@Transactional)에 드러나 어디까지 한 번에 처리되는지 바로 확인할 수 있습니다.
