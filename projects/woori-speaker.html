02

태블릿 녹취에서 화자별 STT까지

개발 관점

마이크가 하나라 채널 분리는 엔진에서 하지 않고, 완본 저장 후 별도 스레드로 GPU 서버에 보내게 개발했습니다. 돌아온 PCM부터는 기존 PC 녹취와 같이 TCP로 STT에 넘기고, 결과는 Kafka로 받게 했습니다.

② 프록시

태블릿 프로젝트에서 만든 중계망 Proxy를 이 업로드 구간에 맞게 수정했습니다. 녹취 파일은 Netty TCP로 주고받고, 유휴 세션은 ping-pong으로 유지합니다.

③ ④ Round Robin

화자분리 서버는 2대이고, 앞단은 Round Robin입니다. 서버 안에서 WebSocket으로 Python 모델을 호출해 MP3를 RX·TX PCM으로 나눕니다. 모델은 서버에 연동했고, 파일 하나의 연결이 그 서버에 머물기 때문에 Round Robin으로 나눕니다.

⑤ ⑦ STT

녹취 엔진은 STT와 TCP로 start · end · connection을 주고받은 뒤 음성 패킷을 보냅니다. STT 결과는 Kafka로 돌아와, 이 구간부터 기존 PC 녹취 코드를 그대로 씁니다.

⑧ ⑩ 웹뷰

웹뷰는 중계망 JEUS를 거쳐 녹취 엔진 WebSocket 서버에 붙습니다. 라이선스 발급·검증과 STT·TA 결과를 이 연결로 받습니다.

04

트러블슈팅

01중계 프록시 세션이 주기적으로 끊김

문제

녹취 업로드 중 중계망 프록시에서 idle timeout이 처리되지 않아 세션이 주기적으로 끊겼습니다.

원인

유휴 연결에 대한 timeout 처리가 없어, 잠시 데이터가 없으면 세션이 종료됐습니다.

해결

태블릿 때 만든 Proxy를 수정해 timeout을 처리하고, ping-pong으로 유휴 세션을 유지했습니다.

결과

업로드 세션이 주기적으로 끊기지 않게 됐습니다.

02세션 참조가 남아 힙 메모리가 초과됨

문제

멀티스레드로 TCP·WebSocket 세션을 함께 관리하면서, 객체 참조와 정리되지 않은 세션 때문에 OOM이 자주 발생했습니다.

원인

연결이 끝난 세션과 버퍼 참조가 스레드마다 남아 힙이 계속 늘었습니다. Netty 버퍼는 release하지 않으면 회수되지 않습니다.

해결

세션 보관소를 싱글톤으로 두고, 채널이 닫힐 때 세션을 빼도록 구조를 다시 짰습니다. ChannelGroup이 닫힌 채널을 스스로 제거하고, 받은 버퍼는 release로 참조를 놓습니다. JVM 힙도 함께 늘렸습니다.

결과

힙을 늘린 상태에서, 참조가 쌓이던 기존 OOM은 다시 발생하지 않았습니다.
